Repl Toolkit uses **Microsoft.Extensions.DependencyInjection** through <ApiRef uid="Repl.ReplApp" /> (the `Repl.Defaults` package). `Repl.Core` (<ApiRef uid="Repl.CoreReplApp" />) has no DI container — services are passed explicitly.

## Service registration

```csharp
var app = ReplApp.Create(services =>
{
    services.AddSingleton<IContactStore, InMemoryContactStore>();
    services.AddSingleton(typeof(IStore<>), typeof(InMemoryStore<>));  // open generic
    services.AddScoped<ICurrentUser, SessionUser>();                   // per-session
}).UseDefaultInteractive();
```

## Injecting into handlers

Handler parameters that match registered services are injected automatically. No attribute is needed:

```csharp
app.Map("list", (IContactStore store) => store.All());

app.Map("add {name} {email:email}",
    (string name, string email, IContactStore store) =>
    {
        store.Add(name, email);
        return Results.Success($"Added {name}.");
    });
```

Repl resolves parameters in a specific order — route values, then options, then DI. If a parameter name matches a route segment, it gets the route value. Otherwise Repl tries DI.

Use <ApiRef uid="Repl.FromServicesAttribute" label="[FromServices]" /> to force DI resolution when disambiguation is needed:

```csharp
app.Map("show {id}", ([FromServices] IContactStore store, int id) => store.Get(id));
```

## Context values and `[FromContext]`

Route values from parent contexts are available in child scopes via <ApiRef uid="Repl.FromContextAttribute" label="[FromContext]" />:

```csharp
app.Context("project {id:int}", project =>
{
    project.Map("status",
        ([FromContext] int id, IProjectService svc) => svc.GetStatus(id));

    project.Map("archive",
        ([FromContext] int id, IProjectService svc) =>
        {
            svc.Archive(id);
            return Results.Success("Archived.");
        });
});
```

<ApiRef uid="Repl.FromContextAttribute" label="[FromContext]" /> binds by parameter name matching the route segment name.

## Prefer static lambdas

Use `static` lambdas to avoid accidental closures. All services should be injected, not captured:

```csharp
// Good — static, services injected
app.Map("list", static (IContactStore store) => store.All());

// Avoid — captures 'store' from outer scope
var store = new ContactStore();
app.Map("list", () => store.All());
```

Static lambdas prevent accidental closures and make handlers independently testable.

## Service lifetimes in Repl

<SessionScopes />

| Lifetime | Scope in Repl |
|---|---|
| `Singleton` | Shared across all sessions and all commands |
| `Scoped` | One instance per session: one `Run*` call (a CLI invocation, an interactive run, a Telnet or WebSocket connection), or one client connection under MCP, except a server built from a reused `BuildMcpServerOptions()` result, where one scope serves every client |
| `Transient` | New instance per resolution |

Use `Scoped` for per-user state (shopping cart, authentication context, cursor position). Use `Singleton` for shared data stores. A `Scoped` disposable is disposed when its session ends, so do not keep a reference to it beyond the session.

Two traps follow from that boundary:

- A `Singleton`, or a module's constructor, that injects a `Scoped` service captures the first session's instance for the life of the app. Inject the scoped service into the handler instead.
- Under MCP, one connection can run several tool calls at once, so a `Scoped` instance can be entered concurrently. Make it thread-safe.

When the caller's provider already is the session, such as a Blazor circuit or an ASP.NET Core request scope, set `ReplRunOptions.SessionScope` to <ApiRef uid="Repl.SessionScopeBehavior" label="SessionScopeBehavior.CallerOwned" /> so the run resolves from it instead of opening a second scope beside it. The repository's [best practices](https://github.com/yllibed/repl/blob/v0.12.0/docs/best-practices.md#pick-the-lifetime-that-matches-the-boundary) cover the details, including the one MCP hosting shape that has no per-connection scope.

<Aside type="note">
**Changed in 0.12.** Before 0.12, Repl opened no scope at all: one `Scoped` instance served every command and every hosted session until the process ended.
</Aside>

<Aside type="caution">
  **Singleton stores must be thread-safe.** In hosted sessions (WebSocket, MCP server), multiple sessions run concurrently and call into the same Singleton instance simultaneously. A store backed by `List<T>` or `Dictionary<K,V>` will race and corrupt. Use `ConcurrentDictionary<K,V>`, an `ImmutableList<T>` with replacement, or a `lock`-guarded wrapper. If the store is per-user, register it as `Scoped` instead.
</Aside>

## Global options

Global options are flags available on every command invocation, parsed before the route:

```csharp
app.Options(o =>
{
    o.Parsing.AddGlobalOption<bool>("verbose");

    // With aliases, default value, and a help description
    o.Parsing.AddGlobalOption<string>(
        "tenant", aliases: ["t"], defaultValue: null,
        description: "Tenant to operate on.");
});
```

Custom global options appear in `--help` under the `Global Options:` section, with their description (or `Custom global option.` when none was given). Default values are intentionally not displayed in help.

Access them in DI factory registrations:

```csharp
builder.Services.AddSingleton<ITenantClient>(sp =>
{
    var globals = sp.GetRequiredService<IGlobalOptionsAccessor>();
    return new TenantClient(globals.GetValue<string>("tenant", "default")!);
});
```

For many global options, use a typed class:

```csharp
app.UseGlobalOptions<MyGlobalOptions>();

// then inject anywhere
app.Map("info", (MyGlobalOptions opts) => opts);
```

**Note:** Singleton factories are resolved once. If a global option can change between REPL commands (e.g. `--tenant` can be toggled interactively), inject <ApiRef uid="Repl.IGlobalOptionsAccessor" /> directly and read at call time rather than in the factory.

## Modules and DI

<ApiRef uid="Repl.IReplModule" /> implementations are resolved from DI:

```csharp
builder.Services.AddSingleton<AuditModule>();
// ...
app.MapModule<AuditModule>();
```

This lets modules declare their own dependencies in constructors — the same way any other DI service does.
