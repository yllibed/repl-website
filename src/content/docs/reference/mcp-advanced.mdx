`Repl.Mcp` is built on the official `ModelContextProtocol` C# SDK, version 2.2. The basics — tools, resources, prompts, MCP Apps, behavioral annotations — are covered in [MCP In Depth](/reference/mcp-concepts/). This page goes one level deeper: the legacy direct access to sampling, elicitation and client roots, dynamic tool compatibility, custom transports, HTTP hosting, protocol revisions, and operator diagnostics.

<Aside type="caution" title="Not for new applications">
[Sampling](#programmatic-sampling), [elicitation](#programmatic-elicitation) and [client roots](#client-roots-and-soft-roots) are legacy on MCP `2026-07-28`; each section says what to use instead. That revision also replaces the requests a server sends to its client with [multi round-trip requests](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/mrtr) (SEP-2322), which Repl 0.12 has not adopted yet ([version notes](https://github.com/yllibed/repl/blob/v0.12.1/docs/mcp-reference.md#sdk-and-protocol-versions)). Do not count on these three features with a host on that revision.
</Aside>

## Programmatic sampling

<Aside type="caution">
Sampling is deprecated by MCP `2026-07-28` ([SEP-2577](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2577)). The specification keeps it for at least twelve months, and the SDK may drop it in a future version; Repl keeps it for hosts that still use it. A new application that needs a model's judgment calls its LLM provider's API directly, as the specification suggests, or takes the result as a tool argument.
</Aside>

MCP sampling lets your server ask the connected AI client to produce an LLM completion. The client uses its own model and returns the generated text.

Inject <ApiRef uid="Repl.Mcp.IMcpSampling" /> into any command handler:

```csharp
using Repl.Mcp;

app.Map("classify {text}",
    async (string text, IMcpSampling sampling, CancellationToken ct) =>
    {
        if (!sampling.IsSupported)
            return Results.Error("sampling_unavailable",
                "This tool requires an AI client with sampling support.");

        // Note: `text` is interpolated directly into the prompt.
        // Cap length and consider structural separation if the source is untrusted.
        var category = await sampling.SampleAsync(
            $"Classify the following text with one word (positive/negative/neutral): \"{text}\"",
            maxTokens: 10,
            cancellationToken: ct);

        return Results.Success($"Category: {category}");
    })
    .WithDescription("Classify text sentiment via LLM sampling.")
    .LongRunning();
```

**Interface:**

```csharp
public interface IMcpSampling
{
    bool IsSupported { get; }   // true iff the client declared Sampling capability

    ValueTask<string?> SampleAsync(
        string prompt,
        int maxTokens = 1024,
        CancellationToken cancellationToken = default);
}
```

`SampleAsync` returns `null` when the client does not support sampling. Always check `IsSupported` or guard on the nullable return before acting on the result.

**Current limitations:** single-message, text-only. The wrapper does not expose system prompts, temperature, model preferences, or multi-turn conversation — those are available in the underlying SDK if you need them.

**Design guidance:** prefer passing all necessary data as route parameters and returning a structured result rather than relying on sampling for core logic. Sampling is best for tasks where LLM judgment genuinely adds value and the command can degrade gracefully without it (as in the [CSV import sample](https://github.com/yllibed/repl/tree/v0.12.1/samples/08-mcp-server) in `samples/08-mcp-server`).

## Programmatic elicitation

<Aside type="caution">
Elicitation stays in MCP `2026-07-28`, but that revision carries it inside [multi round-trip requests](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/mrtr): the server answers `input_required`, and the client retries the call with the answers. `IMcpElicitation` still sends a request of its own; Repl keeps it for hosts that still use it. A new application takes the value as a parameter. For a destructive command, a person's confirmation can only come from the host's tool-approval policy, if it asks at all, and the server cannot tell: `.Destructive()` states the intent, and a `--confirm` option is filled in by the agent, not by a person. Keep a command that must never run without a person present out of MCP with `.AutomationHidden()`.
</Aside>

MCP elicitation lets your server ask a structured question to the user through the connected client. Unlike <ApiRef uid="Repl.Interaction.IReplInteractionChannel" /> prompts (which are automatically triggered by missing parameters), elicitation is explicit: you call it from handler code at the moment you need input.

```csharp
using Repl.Mcp;

app.Map("contacts delete {id:int}",
    async (int id, IMcpElicitation elicitation, ContactStore store, CancellationToken ct) =>
    {
        if (elicitation.IsSupported)
        {
            var confirmed = await elicitation.ElicitBooleanAsync(
                $"Permanently delete contact {id}?", ct);

            if (confirmed is not true)
                return Results.Cancelled("Deletion cancelled by user.");
        }

        store.Delete(id);
        return Results.Success($"Contact {id} deleted.");
    })
    .WithDescription("Permanently delete a contact.")
    .Destructive();
```

**Interface — four typed helpers:**

```csharp
public interface IMcpElicitation
{
    bool IsSupported { get; }

    ValueTask<string?> ElicitTextAsync(string message, CancellationToken ct = default);
    ValueTask<bool?> ElicitBooleanAsync(string message, CancellationToken ct = default);
    ValueTask<int?> ElicitChoiceAsync(string message, IReadOnlyList<string> choices, CancellationToken ct = default);
    ValueTask<double?> ElicitNumberAsync(string message, CancellationToken ct = default);
}
```

`ElicitChoiceAsync` returns the **zero-based index** of the selected choice, or `null` if elicitation is not supported, the user cancels, or the response doesn't match any option.

All methods return `null` when the client does not support elicitation or the user cancels — always handle the null case.

**Current limitation:** each call targets a single field. Multi-field forms (several questions in one request) are not yet supported. If you need them, use sequential calls or open a feature request.

### Sampling vs. elicitation vs. InteractivityMode

| Mechanism | Who provides the response | When to use |
|---|---|---|
| `IMcpSampling.SampleAsync` | LLM (the agent) | Need an AI judgment — classifying, mapping, summarizing |
| <ApiRef uid="Repl.Mcp.IMcpElicitation" /> | User (human) | Need explicit human confirmation or structured input |
| <ApiRef uid="Repl.Interaction.IReplInteractionChannel" /> | User — but automatically wired | Prompting for missing parameters in interactive or REPL mode |
| `InteractivityMode.PrefillThenElicitation` | User, then LLM — as fallback pipeline | Elicitation, then sampling, when a prompt has no prefill value |

In an existing application, use <ApiRef uid="Repl.Mcp.IMcpSampling" /> / <ApiRef uid="Repl.Mcp.IMcpElicitation" /> when you need control over *when* and *how* the question is asked, and <ApiRef uid="Repl.Mcp.InteractivityMode" /> when you want the framework to handle missing parameters. In a new application, take every value as a parameter and keep the default `PrefillThenFail`: when the agent did not pass a value and the prompt has no default, the call then fails visibly instead of being answered with the first choice or an empty value.

## Client roots and soft roots

<Aside type="caution">
Roots are deprecated by MCP `2026-07-28` ([SEP-2577](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2577)); Repl keeps them for hosts that still use them. Soft roots are not their replacement, nor an access boundary: in the pattern below the agent sets them itself. A new application takes the workspace or the path as a parameter and checks it against directories from the server's own configuration, as the specification suggests.
</Aside>

### Native MCP roots

The connected MCP client may advertise workspace roots — the directories or URIs it considers "in scope". Inject <ApiRef uid="Repl.Mcp.IMcpClientRoots" /> to read them:

```csharp
using Repl.Mcp;

app.Map("read {path}",
    (string path, IMcpClientRoots roots) =>
    {
        // Compute the canonical path anchored to each root and reuse it at the read site.
        // Using Path.GetFullPath(path) without a base would anchor on the process CWD,
        // which diverges from the root-anchored check and creates a traversal bypass.
        string? safePath = null;
        foreach (var r in roots.Current)
        {
            var rootPath = r.Uri.LocalPath;
            var full     = Path.GetFullPath(path, rootPath);
            var rel      = Path.GetRelativePath(rootPath, full);
            if (rel != ".." && !rel.StartsWith(".." + Path.DirectorySeparatorChar, StringComparison.Ordinal) && !Path.IsPathRooted(rel))
            {
                safePath = full;
                break;
            }
        }

        if (safePath is null)
            return Results.Error("outside_root",
                $"'{path}' is outside the configured workspace roots.");

        return Results.Text(File.ReadAllText(safePath));
    })
    .ReadOnly()
    .WithDescription("Read a file within the workspace.");
```

`roots.Current` returns the cached list. Use `roots.GetAsync(ct)` to re-fetch from the client on demand (only meaningful when `IsSupported` is true; for clients without native roots it behaves identically to `Current`):

```csharp
var latest = await roots.GetAsync(ct);
```

**IMcpClientRoots:**

```csharp
public interface IMcpClientRoots
{
    bool IsSupported { get; }
    bool HasSoftRoots { get; }
    IReadOnlyList<McpClientRoot> Current { get; }
    ValueTask<IReadOnlyList<McpClientRoot>> GetAsync(CancellationToken ct = default);
    void SetSoftRoots(IEnumerable<McpClientRoot> roots);
    void ClearSoftRoots();
}

public sealed record McpClientRoot(Uri Uri, string? Name = null);
```

`IsSupported` is `true` when the client declared the Roots capability. `Current` returns native roots when supported, or soft roots otherwise.

### Soft roots — the fallback

Soft roots are a Repl-specific application-level convention — not part of the MCP specification. They exist for clients that don't support the native roots capability. `SetSoftRoots` triggers a routing invalidation; any presence predicates that depend on root state are re-evaluated immediately.

The typical pattern: map a `workspace init` command only when the client has no native roots, and use it to register a soft root:

```csharp
using Repl.Mcp;

// This command won't appear in clients that already have native roots support
app.Map("workspace init {path}",
    (string path, IMcpClientRoots roots) =>
    {
        var canonical = Path.GetFullPath(path);
        roots.SetSoftRoots([new McpClientRoot(new Uri(canonical))]);
        return Results.Success($"Workspace set to {canonical}.");
    })
    .WithDescription("Set the working directory for this session (clients without native roots support).");
```

<Aside type="note">
Soft roots are stored per-session, not persisted across sessions. A fresh MCP connection always starts without them. A host that reuses one `BuildMcpServerOptions()` result shares them across the whole process instead.
</Aside>

## Dynamic tool compatibility

Some MCP clients struggle with tool lists that change at runtime — they miss `notifications/tools/list_changed` or don't re-fetch after receiving it. Enable shim mode for maximum compatibility:

```csharp
app.UseMcpServer(o =>
{
    o.DynamicToolCompatibility = DynamicToolCompatibilityMode.DiscoverAndCallShim;
});
```

With the shim active, the agent initially sees only two tools: `discover_tools` (returns the full list of available tools) and `call_tool` (dispatches any tool by name). After calling `discover_tools`, the full tool list is delivered via `notifications/tools/list_changed`.

This is an opt-in fallback — use it only when your target clients are known to have tool-discovery issues. For static tool graphs, leave it at the default (`Disabled`).

## Custom transports

By default, `myapp mcp serve` uses stdio (`StdioServerTransport`). Supply a `TransportFactory` to use any other transport:

```csharp
using ModelContextProtocol.Protocol;

app.UseMcpServer(o =>
{
    o.TransportFactory = (serverName, io) =>
    {
        // io.StandardInput / io.StandardOutput are available if you want to
        // wrap or chain the default streams.
        var (reader, writer) = MyCustomBridge.CreatePair();
        return new StreamServerTransport(reader, writer, serverName);
    };
});
```

The factory receives:
- `serverName` — the value of `ReplMcpServerOptions.ServerName`
- `io` — <ApiRef uid="Repl.IReplIoContext" /> with access to standard input/output streams for the current invocation

`ITransport` is the interface from the `ModelContextProtocol` SDK. Any compliant implementation works — named pipes, WebSocket adapters, in-memory pairs for tests, etc.

## HTTP hosting

The built-in `mcp serve` command serves stdio. To serve MCP over HTTP from an ASP.NET Core host, let the SDK own the transport and apply the Repl catalog to its options. Reference `ModelContextProtocol.AspNetCore`, at the same SDK version as `Repl.Mcp`:

```csharp
using ModelContextProtocol.AspNetCore;
using Repl;
using Repl.Mcp;

var builder = WebApplication.CreateBuilder(args);
builder.Services.AddRepl((_, repl) =>
{
    repl.UseEmbeddedConsoleProfile();
    repl.Map("status", () => "all systems go").ReadOnly();
});

builder.Services.AddMcpServer().WithHttpTransport(http =>
{
    http.SessionMode = HttpServerSessionMode.Stateless;
    http.ConfigureSessionOptions = (context, target, ct) =>
    {
        var repl = context.RequestServices.GetRequiredService<ReplApp>();
        repl.ConfigureMcpServerOptions(target, options => options.ServerName = "MyApi",
            context.RequestServices);
        return Task.CompletedTask;
    };
});

var web = builder.Build();
web.MapMcp("/mcp");
await web.RunAsync();
```

`ConfigureMcpServerOptions` replaces the server identity, capabilities and the tool, resource and prompt collections with the Repl projection, and keeps every other SDK setting: handlers, filters, authentication. In stateless mode the SDK calls it for each request, so always pass `context.RequestServices`: projection and execution then share the request's DI scope. The host owns HTTP, authentication, authorization and shutdown; compose them on the endpoint with its usual policies. `CoreReplApp` has the same helper.

`BuildMcpServerOptions` still returns a ready-made `McpServerOptions` for other hosts. A server built from one reused result has no per-connection DI scope: one `Scoped` instance serves every client. The repository's [MCP transports](https://github.com/yllibed/repl/blob/v0.12.1/docs/mcp-transports.md#scenario-b-mcp-over-http) page covers both paths and what each isolates.

## Protocol revisions

`Repl.Mcp` runs on the official `ModelContextProtocol` SDK 2.2 and serves two protocol revisions from the same server:

| Revision | Era | Served when |
|---|---|---|
| `2026-07-28` | Modern: each request carries its version and capabilities, with no session | Default for a client that does not pin a version |
| `2025-11-25` | Legacy: a session starts with an `initialize` handshake | The client pins it, or opens with `initialize` |

The differences matter mostly to commands that depend on the client. On `2026-07-28` the advertised tool set must not vary between clients, so a module whose presence depends on client roots or sampling is offered to every client or to none. Feedback a command reports rides in the tool result rather than in log notifications. Roots, sampling and logging are deprecated by that revision; Repl keeps them for existing hosts. See [what differs by revision](https://github.com/yllibed/repl/blob/v0.12.1/docs/mcp-conformance.md#what-differs-by-revision).

<Aside type="note">
**Changed in 0.12.** `Repl.Mcp` requires the SDK 2.x; the 1.x and 2.x assemblies cannot coexist. `IMcpFeedback.SendMessageAsync` takes `McpMessageLevel` instead of the SDK's `LoggingLevel`. An unknown resource now answers `-32002` on `2025-11-25` or `-32602` on `2026-07-28`, and an unknown prompt `-32602`, instead of `-32603`. See [upgrading from the 1.x SDK](https://github.com/yllibed/repl/blob/v0.12.1/docs/mcp-reference.md#upgrading-from-the-1x-sdk).
</Aside>

## Operator diagnostics

Some failures are hidden from the MCP client on purpose: an exception message can carry a path or a connection string, and the client only gets `Command failed with exit code N.` `Repl.Mcp` logs the detail for the operator through `Microsoft.Extensions.Logging`, under the category `Repl.Mcp`:

Events 2001 to 2009 cover a tool or resource failure whose detail is withheld (2001), failed catalog rebuilds and roots fetches with their repeats and recoveries, and a catalog that cannot be built because a hidden option is also required (2008).

A failure that can repeat on every request warns once. Under `mcp serve`, standard output carries the protocol, so send logs to standard error. Repeats are logged at Debug, so set the minimum level to see them:

```csharp
var app = ReplApp.Create(services => services.AddLogging(logging => logging
    .SetMinimumLevel(LogLevel.Debug)
    .AddConsole(console => console.LogToStandardErrorThreshold = LogLevel.Trace)));
```

The table of events, with what each one carries, is in [operator diagnostics](https://github.com/yllibed/repl/blob/v0.12.1/docs/mcp-reference.md#operator-diagnostics).

## MCP argument completions

<Aside type="note">
**Not to be confused with LLM completions (sampling).** The MCP `completions` capability is about tab-completing *arguments* — not generating text with a language model.
</Aside>

The MCP `completion/complete` request lets clients (Claude Desktop, VS Code Copilot, etc.) offer inline autocomplete suggestions for tool arguments and resource URI template variables. When a user starts typing a value for a parameter, the client sends a `completion/complete` request to the server; the server responds with a list of candidate values.

**Example scenario:** a tool that takes a `{contactId}` argument could respond to a `completion/complete` request with the list of existing contact IDs — the client then shows them as inline suggestions as the user types.

This is analogous to shell tab-completion (which Repl implements via `completion install`), but at the MCP protocol level, available to any MCP-capable client.

**Status in Repl:** the `completions` server capability is **not yet implemented**. Repl does not advertise it and does not handle `completion/complete` requests. When implemented, it will draw from the same route constraint metadata that powers shell completion — typed constraints (`{id:int}`, `{status:alpha}`) will inform the schema, and handlers will be able to supply dynamic value lists via a new extensibility point.

If you need this feature, open a request at [github.com/yllibed/repl](https://github.com/yllibed/repl/issues).

## Capabilities advertised

When an MCP client connects, Repl announces what the server supports:

| Capability | Status | Notes |
|---|---|---|
| `tools` | Yes — with `listChanged: true` | All non-hidden commands. Dynamic graphs send `notifications/tools/list_changed`. |
| `resources` | Yes — with `listChanged: true` | `.ReadOnly()`, `.AsResource()` and `ui://` registrations. |
| `prompts` | Yes — with `listChanged: true` | `.AsPrompt()` commands and `options.Prompt(...)` registrations. |
| `logging` | Yes | Used by `IReplInteractionChannel.WriteNoticeAsync` / `WriteWarningAsync` etc. Deprecated on `2026-07-28`, where feedback rides in the tool result. |
| MCP Apps (`experimental`) | Conditional | Advertised when `EnableApps = true` or `ui://` resources are present. |
| `sampling` | Client capability | Repl **consumes** this. `IMcpSampling.IsSupported` reads it. Deprecated on `2026-07-28`. |
| `elicitation` | Client capability | Repl **consumes** this. `IMcpElicitation.IsSupported` reads it. Carried by multi round-trip requests on `2026-07-28`. |
| `roots` | Client capability | Repl **consumes** this. `IMcpClientRoots.IsSupported` reads it. Deprecated on `2026-07-28`. |
| `completions` | Not implemented | Argument autocomplete via `completion/complete` — not yet exposed. See [MCP argument completions](#mcp-argument-completions) above. |
