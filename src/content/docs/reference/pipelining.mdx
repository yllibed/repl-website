## The execution pipeline

Every command invocation goes through a 12-stage pipeline. Understanding it lets you hook in at the right stage and reason about where errors come from.

1. **Global option parsing** — `--help`, `--output:format`, `--answer:*`, custom globals
2. **Prefix resolution** — abbreviated command names
3. **Pre-execution handling** — shell completion, help rendering, ambient commands
4. **Route resolution** — matches tokens to registered routes
5. **Banner rendering** — suppressed in CI and non-interactive runs
6. **Command option parsing** — `--name value`, `@responsefile`, `--no-*`
7. **Argument binding** — `CancellationToken`, attributes, groups, route, DI, positional, defaults
8. **Context validation** — optional validation delegates on contexts
9. **Middleware and handler** — your `Use()` chain, then the handler
10. **Result processing** — unwraps `IExitResult` and `EnterInteractiveResult`; page sources are materialized here (see [Result-Flow Paging](/reference/result-flow-paging/))
11. **Output transformation** — format selection and rendering
12. **Exit code** — the outcome kind mapped by `ReplOptions.ExitCodes`, or `n` from `Results.Exit(n)`

## Middleware

Middleware wraps resolved commands. To adapt raw arguments, intercept a parsed invocation, or validate input before routing completes, see [Advanced Input & Startup](/reference/advanced-input-startup/).

Register middleware with `app.Use(...)`. The delegate receives a <ApiRef uid="Repl.ReplExecutionContext" /> (with `Services`, `Items`, and `CancellationToken`) and a <ApiRef uid="Repl.ReplNext" /> delegate to invoke the next stage:

```csharp
app.Use(async (context, next) =>
{
    var logger = context.Services.GetRequiredService<ILogger<Program>>();
    var sw = Stopwatch.StartNew();
    await next();
    logger.LogInformation("Command completed in {Elapsed}ms", sw.ElapsedMilliseconds);
});
```

Middleware runs between argument binding (step 7) and your handler (step 9). Chain multiple `Use(...)` calls — they execute in registration order.

### Authentication middleware example

Resolve your auth service from `context.Services`. If the check fails, short-circuit by not calling `next()`:

```csharp
app.Use(async (context, next) =>
{
    var auth = context.Services.GetRequiredService<IAuthService>();
    if (!auth.IsAuthenticated)
        throw new UnauthorizedAccessException("Not authenticated. Run 'auth login' first.");

    await next();
});
```

<Aside type="caution">
<ApiRef uid="Repl.ReplExecutionContext" /> exposes `Services`, `Items`, and `CancellationToken` — access any service via `context.Services.GetRequiredService<T>()`. To scope auth guards to specific contexts, use per-context validation delegates rather than inspecting route strings in middleware.
</Aside>

### Logging middleware

```csharp
app.Use(async (context, next) =>
{
    var logger = context.Services.GetRequiredService<ILogger<Program>>();
    logger.LogDebug("Executing command");
    try
    {
        await next();
    }
    catch (Exception ex)
    {
        logger.LogError(ex, "Command threw");
        throw;
    }
});
```

## Scripting and automation

### One-shot CLI invocation

Every command works as a one-liner. Combine with shell pipes for scripting:

```bash
# Export contacts and pipe to jq
myapp contacts list --json | jq '.[] | select(.email | endswith("@example.com"))'

# Import from a file
myapp contacts import contacts.csv

# Chain with standard Unix tools
myapp orders list --json | jq '.[].id' | xargs -I{} myapp orders {} archive
```

### Response files

Group complex invocations in a file:

```bash
myapp @deploy.rsp
```

`deploy.rsp`:
```text
deploy
--environment
production
--region
us-east-1
--confirm
```

Response files are space-transparent (one token per line) and non-recursive.

### Pre-filled prompts for CI

Use `--answer:*` to supply interactive prompts from environment variables or scripts:

```bash
# In CI — no user present
myapp release publish \
  --answer:confirm=yes \
  --answer:version=$VERSION
```

### Machine-readable help in scripts

```bash
# Discover available commands
myapp --help --json | jq '.commands[].name'

# Get parameter schema for a command
myapp contacts add --help --json | jq '.parameters'
```

## Integrating with ASP.NET Core

Repl integrates natively with `WebApplicationBuilder`. Register the command graph with `AddRepl`, and run sessions against the request's services so commands and HTTP endpoints resolve the same registrations:

```csharp
var builder = WebApplication.CreateBuilder(args);
builder.Services.AddSingleton<IContactStore, ContactStore>();

// Repl command graph — same services as the web endpoints
builder.Services.AddRepl((_, repl) =>
{
    repl.UseEmbeddedConsoleProfile();
    repl.Map("contacts list", static (IContactStore store) => store.All());
});

var webApp = builder.Build();
webApp.UseWebSockets();
webApp.MapGet("/api/contacts", (IContactStore store) => store.All());  // REST API
webApp.Map("/ws/repl", async (HttpContext context, ReplApp repl) =>     // REPL sessions
{
    using var socket = await context.WebSockets.AcceptWebSocketAsync();
    await ReplWebSocketSession.RunWithServicesAsync(repl, socket, context.RequestServices,
        new ReplRunOptions { SessionScope = SessionScopeBehavior.CallerOwned },
        cancellationToken: context.RequestAborted);
});

await webApp.RunAsync();
```

The REPL command `contacts list` and the REST endpoint `/api/contacts` share the same `IContactStore` instance. [Hosting Remote Sessions](/cookbook/hosting-remote/) shows the complete endpoint, with request validation and shutdown handling.

## Hosting background services

A Repl app can host `IHostedService` / `BackgroundService` implementations alongside its command surface. Register them as you would in any .NET host:

```csharp
var app = ReplApp.Create(services =>
{
    services.AddSingleton<IContactStore, ContactStore>();
    services.AddHostedService<CacheWarmupService>();   // runs on startup
    services.AddHostedService<SessionCleanupService>(); // runs in background
});
```

Enable hosted service lifecycle so Repl starts and stops them:

```csharp
return await app.RunAsync(args, options: new ReplRunOptions
{
    HostedServiceLifecycle = HostedServiceLifecycleMode.Head,
});
```

This is most useful for **REPL and MCP server** scenarios where the process runs indefinitely — background services have a long lifetime alongside the interactive session. In CLI mode the process exits after the command completes, so hosted services run only for the duration of that invocation.

```csharp
public class SessionCleanupService(IContactStore store) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        while (!ct.IsCancellationRequested)
        {
            await Task.Delay(TimeSpan.FromHours(1), ct);
            store.PurgeExpiredSessions();
        }
    }
}
```

## Signal handling and graceful shutdown

With `UseCliProfile()` or `UseDefaultInteractive()`, Ctrl+C or `SIGTERM` cancels the `CancellationToken` passed to a one-shot handler. Long-running commands should honor it:

```csharp
app.Map("process {file}", async (string file, CancellationToken ct) =>
{
    await foreach (var record in ReadRecords(file, ct))
    {
        ct.ThrowIfCancellationRequested();
        await ProcessRecord(record, ct);
    }
    return Results.Success("Done.");
});
```

[Exit Codes & Signals](/reference/exit-codes/#process-signals) covers the exit codes, the token's lifetime, and how to opt in or out per run. Hosted sessions end when their own token is cancelled; [Hosting Remote Sessions](/cookbook/hosting-remote/#how-a-session-ends) shows how to tie it to host shutdown.

## Error handling

Errors flow through the pipeline as typed <ApiRef uid="Repl.Results" />:

```csharp
app.Map("pay {amount:double}", async (double amount, IPaymentService payments) =>
{
    if (amount <= 0)
        return Results.Validation("Amount must be positive.");

    var result = await payments.ChargeAsync(amount);

    return result.IsSuccess
        ? Results.Success($"Paid {amount:C}.")
        : Results.Error("payment_failed", $"Payment failed: {result.Message}");
});
```

Unhandled exceptions are caught at stage 9 and reported as an error result in the requested format. The run ends as a `HandlerException` outcome.

### Exit codes

Every run ends in exactly one <ApiRef uid="Repl.ReplExecutionOutcomeKind" />. The process exit code is read from `ReplOptions.ExitCodes`, not from the handler's return value. A handler that must pick its own code returns `Results.Exit(n)`, which bypasses the table:

```csharp
return Results.Exit(42);   // explicit exit code
```

<Aside type="tip">
Use `Results.Cancelled(...)` for user-initiated cancellations and `Results.Validation(message)` for bad input — they render with distinct messages and are semantically separate from `Results.Error(code, message)`. All three are handler failures. A command that ran to completion but found failures, such as a test run, returns `Results.CompletedWithFailures(report)` instead.
</Aside>

[Exit Codes & Signals](/reference/exit-codes/) covers the full table, the resolver hook, codes declared by a module, and process signals.
